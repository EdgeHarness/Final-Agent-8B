# Audit, 2026-08-11

Backend and frontend pass over Agent Lab, looking for constraints that are not
earning their place and pipelines that only work on one machine or one model.
Everything marked FIXED has a test in `standalone/tests/test_harness.py` that
failed before the change. Findings were produced two ways: reading the backend,
and running the app as a user with the shipped presets.

Run the suite from `standalone/`:

    ../.venv/bin/python -m tests.test_harness

58 tests. There were none before this pass, against 3,882 lines of Python.

---

## 1. The product only ran on Windows

FIXED. `harness/fs_tools.py`.

- `run_command` shelled out to `powershell.exe` with no platform check. The
  flag existed, the tool was advertised in the system prompt, and the first
  call raised FileNotFoundError on every machine that is not Windows, which is
  every machine this has been developed on.
- The write deny-list was five Windows absolute paths plus the lab machine's
  own `C:\Users\Lab User\SAIL\...` folders. On macOS and Linux not one of them
  exists, so the guard matched nothing: a working root of `/` had no protected
  locations at all. It now follows the platform, and the two entries that are
  about this project rather than the OS are derived from `__file__`, so they
  hold wherever the code is checked out.
- Every path example was backslashed (`notes\todo.txt`). A model copies an
  example verbatim, so on POSIX the first write made one file literally named
  `notes\todo.txt`.
- `enable()` takes a `deny=` list so a caller can protect more.

## 2. Profiles were chosen by family, so size was ignored

FIXED. `harness/profiles.py`.

The fallback took the first listed profile whose family matched, and `llama3.2`
lists `1b` first. A `llama3.2:11b` was therefore handed the 1B's
format-survival tuning: planning off, verifier off, replies capped at 350
tokens. Resolution is by parameter count now, parsed from the tag, which is the
thing these knobs actually answer to. A same-family entry still wins, but only
when its size matches too. Borrowed tuning says so in its label, so a banner
never claims a gemma is a tuned Llama.

This also gives `gemma3`, `phi4-mini` and `qwen3` a sensible profile. All three
are offered in the download rail and none had one.

## 3. Three ways the agent produced a confident wrong answer

All three were found by running the shipped preset tasks, not by reading code.

### 3a. The verifier could not see what the actions returned

FIXED. `harness/agent.py`.

It was shown call signatures only, so it could not tell that the file it was
about to demand already existed. On "build a spreadsheet of the three regions",
it answered `complete: false` against a finished task, the 8B redid the work,
and the rerun wrote a second spreadsheet. One task, two files for the user.

With results in the evidence and a prompt that says to judge only the
requirements the task states, the same task went from 13 calls and 24.5s to 6
calls and 12.1s, and produced one file.

### 3b. A memory outranked looking

FIXED. `harness/agent.py`, `harness/tools.py`.

An earlier run had saved "Wednesday has 0 meetings". On "summarize my Wednesday
meetings and message Jordan", the agent read that memory and messaged a
colleague that their Wednesday was clear. The calendar held three meetings.

The injected block said "apply them when relevant", which reads as an
instruction. Memories are presented as dated hints now, and `save_memory` says
not to store what changes. The false fact has been removed from the demo agent.

### 3c. A date the model formatted itself was never checked

**Generalized 2026-08-11 (loop pass):** the first fix only knew weekdays.
The failure is identical for every date expression the normalizer understands,
so the check now extracts all of them from the task ("wednesday", "tomorrow",
"July 23", "7/23", literal ISO) with `task_dates()`, resolves each through the
SAME normalize_date the arguments go through, and compares when the task names
exactly one distinct date. Reusing the normalizer is the point: the check and
the repair can never disagree about what "next tuesday" means.

Original finding:

FIXED. `harness/agent.py`.

`normalize_date` turns "wednesday" into the right date, but returns
immediately when the model has already written a well-formed `YYYY-MM-DD`. The
8B did the arithmetic itself, sent `2026-07-27` for Wednesday (a Monday), and
every tool answered honestly for the wrong day.

A weekday named exactly once in the task is now checked against any date in the
call, and corrected the way a bad parameter is. Narrow on purpose: "move my
Wednesday meeting to Friday" names two and is left alone.

## 4. The worst failure this app can produce

PARTLY FIXED. `harness/agent.py`.

Asked "build a spreadsheet of my July receipts with a total", the 8B skipped
the inbox entirely and invented 100 / 200 / 300 / 400 / 500. The real receipts
are $230.00, $87.50 and $412.30. It then saved the invented total to long-term
memory as a fact, and the run reported success, because every check downstream
can see that a file was written and none can see that the numbers in it were
made up.

The harness had one piece of evidence it was throwing away: the plan. If the
plan named a read before its first write and the model writes without having
read anything, the loop now says so once and then gets out of the way. After
this change the same preset reads all three receipt emails and builds the sheet
from the real amounts.

This is a mitigation, not a fix. Nothing in the system verifies that the
content of a generated file came from the user's data. Options, none taken yet:

- Ask the verifier to check figures against the observations, not just that
  actions happened. Costs a call and a strong verifier.
- Have the UI mark a file written before any read as unsourced.
- Keep a per-run note of which observations a write drew on.

## 5. Unnecessary constraints removed

- **Real-folder call budget** was a flat 40 for every model, a number chosen
  for the 8B and applied to a 1B (2.2x its own tuned budget) and a 32B. It
  scales with the profile now and leaves the 8B at exactly 40.
- **A failed call spent its full repeat budget.** The budget exists so a model
  can look at something twice; that reasoning only holds for a call that
  worked. An identical call that errored against an unchanged world returns the
  identical error, so a budget of three bought three copies of one failure.
  Observed: an 8B spent three of twenty calls on one bad email id.
- **Memory lost every fact in the folder if one line was torn.** The agent
  appends to that file mid-run, so a crash leaves a partial line, and the
  reader raised on it. One torn line made the agent folder unopenable forever.
  The web server's reader had always skipped bad lines; the harness had not.
- **Memory stored the same fact twice.** Only three or four facts reach the
  system prompt, so a model re-saving one preference every run crowded out
  everything else it knew.
- **Memory search missed its own example.** Retrieval was exact token overlap,
  so the shipped preset "Remember that I prefer meetings after 14:00" could
  never be recalled by a task mentioning "meeting preferences": meeting and
  meetings are different strings. Prefix matching from four characters up.

## 6. Things that are configured but not reachable

- **The MCP bridge is orphaned.** `harness/mcp_bridge.py` is 373 written and
  careful lines: stdio JSON-RPC, a draft mode that drops any tool that can
  transmit to a person, per-server allow and drop lists, confirmation on every
  write. Nothing imports it. Not the runner, not the server, not a config file.
  This is the largest gap between what the product says and what the backend
  can do: the empty state says "run your inbox, calendar and documents", and
  the only inbox reachable today is the simulated one. Wiring it needs a UI
  surface for server configuration and a decision about the privacy claim,
  since model inference stays local but the tools would reach Google or
  Microsoft. Left for a decision rather than done quietly.
- **The `deep` tier is advertised and never called.** `default_roles` names
  `qwen2.5:14b` for a role `run_harness` never asks for, and the tag did not
  have to be installed to be listed. The banner now separates roles the loop
  calls from roles that are only configured.
- **Office files ignore the working root.** With a real root and
  `--with-office`, `create_presentation` and `create_spreadsheet` write into
  the agent's own folder, not the folder the user pointed at, and nothing said
  so. The prompt now says it. Whether they should follow the root instead is a
  product decision: the browser preview reads from the agent folder, so moving
  them breaks the preview without more work.

## 6b. Loop pass, iteration 3: the failure surface and value repair

- **A refused model call now names the model and quotes the server's own
  sentence.** raise_for_status() threw the response body away, so what reached
  the user was "404 Client Error: Not Found for url
  http://127.0.0.1:11434/api/chat" - a loopback URL nobody can act on - while
  the body said "model 'x' not found, try pulling it first". Fixed at the
  client (`harness/llm.py`), so every caller inherits it: the verifier's
  fail-open and the runner's error event already handle RuntimeError.
- **Deterministic repair extended from parameter names to values**
  (`harness/office.py`). Models regularly send spreadsheet rows as a list of
  OBJECTS - keys are the header, values the rows - and slides as bare strings.
  Both are unambiguous, and rejecting them cost a whole model call to repair a
  shape the code can convert byte-for-byte. Objects with differing keys are
  still rejected, not guessed at.
- **run_raw is now covered.** bench/ calls it and nothing exercised it; the
  crash-safe snapshot restructured its loop, so two tests pin the behaviour.

## 6c. Loop pass, iteration 4: the server layer

- **Stop lost the world.** The Stop button sends SIGTERM, and Python's default
  reaction is to die without unwinding - so the crash-safe snapshot from the
  earlier fix never ran for a STOPPED run, which is the far more common way a
  run ends early. The runner turns SIGTERM into SystemExit(143): the finally
  runs, the snapshot lands, the process still exits nonzero. Verified live: a
  message sent before Stop now survives it in state.json.
- **Reset mid-run silently undid itself.** The live subprocess holds the world
  in memory and snapshots on exit, so the freshly deleted state.json
  reappeared seconds later carrying the pre-reset world. The user saw the
  reset succeed and then watched the old inbox come back. Same contract as
  starting a second run now: one thing owns the folder at a time, 409
  otherwise. Verified live.

## 7. Frontend

- **Glass is now one seam and a preference.** Every floating surface blurs
  through `--glass-blur`, so it toggles in one place. Off swaps `--glass` for
  the solid panel colour and nothing moves.
- **Glass was applied only where something is actually in front of something
  else**: the composer, the two popovers, the viewer, the preset chips (they
  ride the dock, which floats over the transcript), and the workspace pane
  below 1100px, which is the width where it stops being a column and becomes a
  sheet on top of the run. The rail, the tab bar and the touched strip do not
  overlap anything at full width, so a blur there would be a flat tint. Left
  opaque on purpose.
- **Preferences replaced the theme toggle.** A two-state button could not
  express "follow the system", so once you had clicked it once you were pinned
  to a theme forever. Three explicit choices plus the glass switch, both
  persisted.
- **Four of eleven timeline rows said only "no reasoning given."** A model call
  with no `thought` is ordinary; the tool row under it is what the call was
  for. The row keeps its timing and drops the sentence.

### Checked and not a defect

- `documentElement.scrollWidth` reads about 125px over the viewport with the
  workspace open. It is the preset strip's own scroll width, `body` clips, and
  `window.scrollX` stays 0. Nothing is reachable or visible.

## 6d. Loop pass, iteration 5: README reconciliation and the components list

The README described behaviour the code no longer has: 14 tools (now 16), a
flat 14/40 call budget (profile-scaled since the first pass), a dedupe rule
without the failed-call exception, and a verifier that saw signatures without
results. All corrected in place; the architecture prose was left alone.

Verified in passing that `agents/8b/run_agent.py` - the lab entry point -
still works against the reworked harness: profile resolution, budget, a full
clean run. One hazard found doing it: **it has no flag validation**, so
`run_agent.py --help` does not print help, it RUNS "--help" as the task,
spending 13 model calls and mutating the persistent world. Left unfixed
because that file must stay byte-identical to the lab machine's copy; fix it
there first.

### Components worth adding, in priority order

1. **MCP bridge wiring** (`mcp_bridge.py` exists, orphaned). The product says
   "run your inbox"; the only inbox is simulated. Needs: a config surface
   (which servers, which mode), the draft-mode default, and a decision on the
   privacy line, since inference stays local but tools would not.
2. **Provenance for writes.** The plan-hold nudges reduce invented content;
   nothing yet verifies a written file's figures against the observations the
   run actually made. Cheapest honest version: the end card lists which reads
   preceded each write ("built from e2, e3, e5").
3. **A queue, or an honest 409 UI.** One run at a time is right for one
   machine, but the UI just fails the second Run press; it should say who is
   running and offer Stop.
4. **Memory provenance and expiry.** A fact cannot be traced to the run that
   saved it, and nothing ever expires. The dated-hint framing helps; a
   `saved by run_NNN on <date>` suffix would let the UI offer "forget this".
5. **CI for the test suite.** 87 tests exist and run in under a second;
   nothing runs them automatically.

## 6e. Loop pass, iteration 6: the preset regression sweep

All six shipped presets, fresh fixtures, on the tree merged with the
teammate's MCP and app-shell work. 6/6 finished. P2 used the new
update_event unprompted; P4 built the receipts sheet from the three real
amounts; P5 replied and booked in 7 calls with no guard firing.

Two findings:

- **The date guard over-fired on preference statements.** "Remember ... never
  on Fridays" is not a date instruction, but the guard resolved "Fridays" and
  then corrected four innocent list_events probes: 14 calls for a task that
  needs four. Generalized fix: the guard checks WRITES only. It exists to stop
  a write landing on the wrong day; a read with a mismatched date is the model
  looking around, and the result comes back as evidence either way.
- **The plan can smuggle unrequested work past the plan-hold guard.** On the
  rerun the model PLANNED the extra work: it saved the preference, then
  cancelled Design review, rescheduled two meetings and messaged Sam,
  "applying" a preference nobody asked it to apply - all per its own plan, so
  the unplanned-write guard rightly stayed quiet. Holding the model to its
  plan is mechanical; holding the plan to the task is a judgment call. The
  honest options both cost a model call: judge the plan against the task
  before acting, or fold "did the task ask for each write?" into the verifier.
  Left open rather than patched - a keyword heuristic here would be exactly
  the kind of narrow fix this pass exists to remove.
